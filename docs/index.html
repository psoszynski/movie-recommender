How semantic search actually works

Keyword search finds the words you typed. Semantic search finds what you meant. This page walks through the mechanics — turning text into vectors, storing them in a relational database, finding the nearest ones, and indexing them so it stays fast — using the real embeddings from a recommender of movies and TV series (16,287 titles).

From text to a point in space

An embedding model reads a piece of text and outputs a fixed-length list of numbers — a vector. Texts with similar meaning get vectors that point in similar directions. The model never sees your database; it only ever sees text.

This is the exact text the recommender composes per movie (EmbedService.BuildDocumentText) — title, year, genres, popular tags, and the TMDB overview. The search_document: prefix tells nomic-embed-text this is a document, not a query.

    03
    
Measuring "close"

    
"Nearest" needs a definition. SQL Server's VECTOR_DISTANCE supports three.
       Drag the two arrows — the numbers update live.

  


  

    

      
      
2-D for illustration. The math is identical in 768-D.

    

    

      

        
cosine used here

        
–

        
1 − cos θ. Only the angle matters; length is ignored. Best default for text embeddings,
           which encode meaning in direction. Range 0 (identical) to 2 (opposite).

      

      

        
euclidean

        
–

        
Straight-line distance between the tips. Sensitive to length. Fine when vectors are
           normalised — then it ranks identically to cosine.

      

      

        
dot (negative inner product)

        
–

        
−(a·b). Cheapest to compute; rewards long vectors. Use when the model is trained for it
           (many are) or vectors are already unit-length.

      

    

  


  

    
Real numbers from the database

    
Cosine distance between actual stored vectors. Smaller = more similar.

Storing and querying in SQL Server

    
The vector lives in a column like any other — next to the title, year and rating you already
       filter on. One query does semantic ranking and relational filtering, in one engine,
       in one transaction.

  


  

    

      
Schema

EF Core 11


public SqlVector<float>? Embedding { get; set; }

// LINQ — translates to VECTOR_DISTANCE
var hits = await db.Movies
    .Where(m => m.Embedding != null && m.Year >= 2000)
    .Select(m => new { m.Title,
        Distance = EF.Functions.VectorDistance("cosine", m.Embedding!.Value, query) })
    .OrderBy(x => x.Distance)
    .Take(10)
    .ToListAsync();

    


    

      
Exact search = a full scan

      
Without a vector index, SQL Server computes the distance for every row,
         then sorts. Press play.

      
      

        
        16,287 rows · 0 compared
      


SELECT TOP(10) Title,
       VECTOR_DISTANCE('cosine', Embedding, @query) AS Distance
FROM   Movies
WHERE  Embedding IS NOT NULL AND Year >= 2000
ORDER BY Distance;

      
    
        
  • Measured on the original 9,742 MovieLens rows: 9 ms, 9,812 logical reads
    • 
        
  • Cost grows linearly with rows: 1M rows ≈ 1 s, 100M ≈ minutes
    • 
        
  • Result is exact — 100% recall, every time
    • 
        
  • Works on SQL Server 2025, Azure SQL, Fabric — no feature flags
    •

Indexing: trading a little recall for a lot of speed not yet used in this repo

    
A B-tree can't index "closest direction in 768-D". Instead, vector indexes build a navigable
       graph: each vector links to a few near neighbours. A query starts at an entry point and
       greedily hops toward the target, touching a tiny fraction of the data. SQL Server 2025 uses
       DiskANN, Microsoft Research's disk-friendly variant.

How you'd turn it on


-- SQL Server 2025: preview feature, must be enabled per database.
-- GA on Azure SQL Database, Fabric SQL and Azure SQL MI (always-up-to-date).
ALTER DATABASE SCOPED CONFIGURATION SET PREVIEW_FEATURES = ON;

CREATE VECTOR INDEX IX_Movies_Embedding
    ON Movies (Embedding)
    WITH (METRIC = 'cosine', TYPE = 'DiskANN');

-- ORDER BY VECTOR_DISTANCE never uses the index. You call it explicitly:
SELECT m.Title, s.distance
FROM   VECTOR_SEARCH(
          TABLE      = Movies AS m,
          COLUMN     = Embedding,
          SIMILAR_TO = @query,
          METRIC     = 'cosine',
          TOP_N      = 10) AS s
ORDER BY s.distance;

RAG — retrieval-augmented generation

      
An LLM only knows what was in its training data and what you paste into the prompt. RAG uses
         the vector search from this page to pick what to paste.

      
    

    

      
Why retrieval instead of fine-tuning

      
    
        
  • Always current — update a row, the next answer uses it; no retraining
    • 
        
  • Permission-aware — the WHERE clause runs before the LLM ever sees a word; row-level security applies
    • 
        
  • Cites its sources — every answer links back to the chunks it was built from
    • 
        
  • Cheap to try — one embedding model, one table, one query; no GPUs on your side
    • 
        
  • Auditable — log the question, the retrieved ids and the answer in the same database
    • 
      

      
What the LLM adds

      
    
        
  • Synthesises several passages into one answer in the user's language
    • 
        
  • Can say "not found in our documents" instead of guessing — if you tell it to
    • 
        
  • Is interchangeable: Azure OpenAI, Foundry, or a local model via Ollama — the retrieval layer doesn't change
    • 
      

    

  


  
Mechanisms that change how an organisation operates

  

    
⌕Find by meaning across silos
One query over tickets, wikis, contracts and chats, regardless of wording, synonyms or language. The "where was that?" tax disappears.

    
⇄Route and triage automatically
Embed an incoming ticket or email, find the nearest already-labelled ones, inherit their team and priority. Classification with zero training.

    
≡Deduplicate and cluster
Near-identical incidents, duplicate supplier records, overlapping policies — anything with cosine distance < 0.1 is a candidate for merging.

    
★Recommend
Exactly for-user: the centroid of what someone read, bought or completed becomes a query. Works for courses, products, articles, job postings.

    
◎Ask-your-data assistants
RAG over internal documents gives staff and citizens a 24/7 answer with a citation, and tells you which questions had no good document.

    
⚠Spot the unusual
A new record whose nearest neighbour is far away is novel: a fraud pattern, an unprecedented complaint, a contract clause nobody has signed before.

    
⊕Hybrid, not either/or
Vectors for meaning, SQL for facts: WHERE Status='open' AND Region='EU' ORDER BY VECTOR_DISTANCE. One engine, one transaction, one backup.

    
⟳Learn what people actually ask
Cluster the query vectors. Dense clusters with poor results show exactly which document, FAQ or course is missing.

    What to get right. Chunking — embed units a human would quote (a paragraph, a ticket, a clause), not whole PDFs.
    Permissions — filter in SQL with the user's identity before ranking; never let the LLM be the gatekeeper.
    Evaluation — keep 50 real questions with known good answers and measure recall@10 on every change of model or chunking.
    Freshness — re-embed only what changed (this repo's EmbeddingText diff does exactly that).
    Honesty — instruct the model to answer only from retrieved passages and to say when they don't cover the question.
